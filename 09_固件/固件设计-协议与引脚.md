## 0. 一句话定位

STM32F103RCT6 扮演 **"哑执行器 + 安全守门人"**：

- **哑**：只认 §3 的 ASCII 行协议，收到明确命令才动，动完发 `EVT` 回报；不猜意图、不自主决策。
- **守门人**：**一切安全判断（软限位、未回原点禁动、急停）都在固件里**。
  这是与上位机（AI）的硬契约 —— **上位机不做兜底，桥只发字节、不做任何安全判断**。

> 为什么这么分：AI 会犯错（幻觉出越界坐标、把轴名写错、命令发一半）。让"最不可能出错的一层"兜住安全问题，是这套架构唯一站得住的理由。

## 3. 线协议规格 v1.0

### 3.1 物理层

| 项 | 值 | 依据 |
|---|---|---|
| 串口 | **USART1**，PA9(TX) / PA10(RX) | 板载 CH340K 就接在这里（bootloader 应答反证，2026-09-21 实测） |
| 参数 | **115200 8N1** | 与桥默认一致 |
| 行尾 | `\n`（兼容 `\r\n`） | |
| 编码 | ASCII | 中文只出现在 `LCD` 透传内容里（UTF-8 或 GBK，随屏） |
| 时限 | **每条命令 ≤100 ms 内必须回一行** | 接口契约第 3 条 |
| 最大行长 | 64 字节（超出丢弃并回 `ERR 10`） | 防缓冲区被灌爆 |

### 3.2 命令表（主机 → 板）

| 命令 | 立即应答 | 完成时异步事件 | 说明 |
|---|---|---|---|
| `PING` | `OK pong` | — | 心跳（桥侧起手第一句） |
| `VER` | `OK fw=0.1.0 proto=1` | — | 版本自描述 |
| `HELP` | `OK commands=PING,VER,STATUS,...` | — | **自描述命令表，方便 AI 自发现**（不靠人记文档） |
| `STATUS` | `OK state=READY homed=XY estop=0 box=101000 pos=1234,567 z=UP grip=OPEN` | — | 一行汇总，字段固定顺序 |
| `GETPOS` | `OK x=1234 y=567 z=1250 grip=900` | — | `z`/`grip` 是舵机脉宽 µs |
| `HOME ALL` | `OK homing` | `EVT HOME_DONE ALL` / `EVT HOME_FAIL <ax> code=16` | 依次 X→Y |
| `HOME X` / `HOME Y` | `OK homing` | 同上 | 单轴回零 |
| `JOG <轴> <步数>` | `OK` | `EVT MOVE_DONE <轴>` | 相对运动，步数带符号，如 `JOG X 200` |
| `MOVE X <步> Y <步>` | `OK` | `EVT MOVE_DONE XY` | 绝对坐标（**未回零一律 `ERR 11`**） |
| `ZUP` / `ZDOWN` | `OK zup` / `OK zdown` | `EVT Z_DONE UP\|DOWN` | 升降到两个标定位（脉宽 2500µs / 500µs） |
| `ZSET <µs>` | `OK set` | — | 直接给舵机脉宽（500~2500，**标定/调试用**） |
| `ZPCT <0~100>` | `OK set` | — | 按行程百分比升降（换机构不用改协议）✅ **M2 实测** |
| `GRIP` | `OK grip` | `EVT GRIP_DONE loaded=0\|1` | 闭爪；`loaded` 由**微动开关**确认触货。⚠️ **M2 未接微动 → 恒报 `loaded=0`（未确认），不是"没夹到"** |
| `RELEASE` | `OK release` | `EVT RELEASE_DONE` | 开爪 |
| `GSET <µs>` / `GPCT <0~100>` | `OK set` | — | 夹爪脉宽 / 百分比（标定用；`GSET` 是 `ZSET` 的夹爪版） |
| `SAFE` | `OK safe z=up grip=open` | — | 显式回安全位（Z 最高 + 夹爪张开） |
| `BOX?` | `OK box=101000` | `EVT BOX_CHANGED box=101000` | 6 路入盒状态（1=有货）。**状态变化会自动推事件**（**20ms 非阻塞采样消抖**，2026-09-22 由 1ms 改，见日志） |
| `MS?` | `OK ms=<n>` | — | 自复位以来的毫秒数。**自证 SysTick 真的在走**（连发两次，差值应≈间隔毫秒）✅ **2026-09-22 实测误差 0.08%** |
| `LCD <内容>` | `OK lcd_sent=<n>B` | — | **原样转发**给串口屏 + **自动补 `FF FF FF`**（淘晶驰每条指令必须以此结尾）。`<n>` = 实际发出字节数（内容长度+3）—— **没接屏时靠它验证载荷有没有被截断、内部空格有没有丢** ✅ 2026-09-22 实测 `LCD page0.t1.txt="A B C"` → `lcd_sent=23B`（20+3） |
| `LCDRAW <hex>` | `OK lcd_raw=<n>` | — | 原样发十六进制字节、**不补** `FF FF FF`（要发二进制/特殊字节时用） |
| `LCDBAUD <1200..921600>` | `OK lcd_baud=<n>` | — | **运行时切屏侧波特率**。⚠️ 淘晶驰出厂常为 **9600**；两边不一致时屏**毫无反应**（不报错、不显示，最难查的一种）→ 用这条现场试，**不用重烧固件** ✅ 2026-09-22 实测 |
| `LCDRD` | `OK lcd_rx=<hex…> count=<n>` | — | 读屏发回来的字节（触摸事件、错误码应答），十六进制 —— **用来判断"屏到底有没有在说话"** ✅ 实测（无屏时 `count=0`） |
| `USART3?` | `OK cr1=… brr=… sr=… crh=… idr=… lcdbaud=…` | — | **屏不动时的第一站**（仿 `TIM3?`）。`idr` 报 **PB10/PB11 的实际电平** —— 空闲时 PB10 必为 1，回环时 PB11 应跟着走；`crh` 应为 `…4B…`（PB10=`0xB` 复用推挽、PB11=`0x4` 浮空） ✅ 实测 |
| `LCDPD <0\|1>` | `OK pb11=pull_down` / `pb11=floating` | — | 把 PB11 切"**下拉输入**"，再看 `USART3?` 的 `idr`：bit11 仍为 **1** ⇒ 有东西在主动驱动它（**屏的 TX 确实接着**）；为 0 ⇒ 那根线没通。**这是排除"浮空输入读到高"假象的客观办法。看完必须 `LCDPD 0` 恢复浮空。** ✅ 实测 |
| `ESTOP` | `OK estop` | `EVT ESTOP reason=cmd` | **立即停**。⚠️ 2026-09-22 实现改为**冻结舵机（不动）**：急停语义是"立刻停住"，此时把 Z 抬起来/张开爪反而是在制造动作。要回安全位请显式发 `SAFE`（或 `CLEAR`） |
| `CLEAR` | `OK cleared` | — | 退出急停/故障；**强制回到"未回零"**，并把舵机送回安全位 |
| `RESET` | （无应答，软复位） | — | 与桥的 `serial_reset(mode="command")` 对齐 |
| `CFG <k> <v>` | `OK` | — | 运行时改参数（速度/加速度/软限位），掉电不保存（v1 从简） |

> 命名取舍说明：**统一用 `轴` 关键字**（`HOME X`、`JOG X 200`）而不是 `HOMEX`/`X200`，是为了让 AI 生成命令时不必记忆多套语法；空格分隔也好人读。
> `GRIP`/`RELEASE` 采纳日志里线路 B 的原提案；`GETPOS` 采纳（并入 `STATUS`）。

### 3.3 应答与错误码

应答统一两种：`OK [payload]` / `ERR <code> [msg]`。

| code | 含义 | 触发场景 |
|---|---|---|
| 1 | 未知命令 | 打错字 —— **不要沉默** |
| 10 | 参数错误 | 轴名非法、步数非数字、行长超限 |
| 11 | **未回原点，拒绝运动** | 上电后直接 `MOVE`（契约第 2 条） |
| 12 | **超出软限位** | 目标或轨迹越界 |
| 13 | 忙 | 正在运动时又来一条运动命令 |
| 14 | 处于急停/故障态 | 必须先 `CLEAR` |
| 15 | 夹爪未触货 | `GRIP` 后微动开关没闭合 |
| 16 | 回零失败/超时 | 找不到原点 |
| 17 | 内部错误 | 兜底 |
| 19 | 屏指令为空 | `LCD` 后面没跟内容 |
| 20 | 屏指令 hex 非法 | `LCDRAW` 的参数含非十六进制字符（或为空） |
| 21 | 屏波特率超范围 | `LCDBAUD` 的参数不在 1200~921600 |

> 说明：**18 号"屏没接"已作废** —— 2026-09-22 串口屏透传已实现（`LCD` 系列），见 §7。

### 3.4 异步事件

格式：`EVT <NAME> [k=v ...]`；自由文本调试信息用 `LOG <text>`。
板子**主动**上报的事件只有两类：① 命令完成/失败 ② **`EVT BOX_CHANGED box=101000`**（入盒状态去抖后发生变化时）。
桥的后台线程会把这些异步行一并缓存，AI 用 `serial_read` 随时取 —— 所以**不需要轮询 `BOX?`**。

### 3.5 为什么"长动作先回 OK、完成再发 EVT"

因为契约要求 **≤100 ms 必须应答**，而"移动到 1234 步"可能要 1~2 秒。先回 `OK` 表示**命令已被接受**（不是"已完成"），完成时用 `EVT` 通知。
→ AI 侧的判据：`OK` = 受理；`EVT *_DONE` = 真的做完了。**这两件事必须分清，否则会写出"以为动完了其实还在走"的 bug。**

## 4. 安全状态机

```
        上电
         │
     ┌───▼────┐  外设初始化完成（电机使能=断、舵机回安全位）
     │  INIT  │
     └───┬────┘
         │ 自检通过
     ┌───▼──────────┐  只接受 PING/VER/HELP/STATUS/GETPOS/BOX?/LCD/
     │ IDLE_UNHOMED │  HOME/CLEAR/ESTOP/RESET  ← 运动命令一律 ERR 11
     └───┬──────────┘
         │ HOME ALL / HOME <轴>
     ┌───▼────┐  回零中；再次收到运动命令 → ERR 13
     │ HOMING │  失败 → FAULT
     └───┬────┘
         │ 全部轴回零完成
     ┌───▼────┐
     │ READY  │◀────────────┐
     └───┬────┘             │ 运动完成
         │ 收到运动命令      │
     ┌───▼────┐             │
     │ MOVING │─────────────┘
     └───┬────┘   运动中被 ESTOP/超软限位 → FAULT
         │
   ┌─────▼─────┐   中断源：急停引脚(EXTI) / ESTOP 命令 / 越限 / 看门狗
   │  ESTOP    │   动作：立刻停脉冲、断电机使能、蜂鸣器长鸣
   └─────┬─────┘   只接受 CLEAR / STATUS / PING
         │ CLEAR
   ┌─────▼─────┐
   │   FAULT   │ → CLEAR 后回 IDLE_UNHOMED（**必须重新回零**）
   └───────────┘
```

**三条不可协商的规矩**：

1. **未回零 → 一切运动命令 `ERR 11`**（上电位置是随机的，不回零就没有坐标系）
2. **软限位在固件里夹**：目标越界 `ERR 12`；**运动过程中也要逐拍检查**，不能只在起点判一次
3. **`CLEAR` 之后必须重新回零** —— 急停可能发生在任意位置，位置可信度必须清零

**急停建议双路**（§11.6）：固件 EXTI 检测只是"软急停"；**强烈建议把急停按钮的常闭触点串进步进驱动器的使能/电源回路**，做到断电级硬急停。软件会死、会跑飞、会被看门狗复位，硬件不会。

## 5. 运动控制

### 5.1 步进脉冲引擎（软件，一个定时器中断）

- `TIM4` 更新中断 @ **20 kHz**（50 µs 一拍）作为唯一时基。
- 每拍为 X/Y 各算一次：按**梯形速度曲线**（加速度 A / 最高速 Vmax / 减速点）决定本拍是否翻转 STEP 引脚。
- 位置计数在软件里（`int32_t`）；Emm42 闭环电机自己会补丢步，软件计数只作轨迹规划用。
- **不在中断里做任何字符串/串口操作** —— 中断只碰 GPIO 和整数。串口收发全在主循环。

> 为什么不用硬件 PWM 发脉冲：硬件 PWM 换速要重算寄存器、且两轴插补很别扭。软件时基换来的是"想加 Z 轴/插补随时能加"，代价是 20 kHz 下 CPU 占用约 3~5%（72 MHz 完全够）。

### 5.2 舵机

- `TIM3` @ **50 Hz**（20 ms 周期），CH3=PB0（Z 轴）、CH4=PB1（夹爪）。**1 µs 分辨率**（TIM3 计数 1 MHz → ARR=19999）。
- 舵机能力范围：脉宽 **500~2500 µs ↔ 0~270°**（DS3225 **270° 版**；180° 版会把行程减半，采购清单已锁 270°）。
- **Z 轴工作行程 = 600 ~ 2400 µs**（`SERVO_Z_LO/HI_US`，`ZPCT 0..100` 映射到这里）✅ **2026-09-22 实测标定**。
  - 标定结论：装入平行四边形连杆、确认机构跟着动之后，**在 500 µs 与 2500 µs 两端机构都还有余量**
    → **限住 Z 轴行程的是舵机自身的内部机械止挡，不是机构**。
  - 因此两端各留 100 µs（≈13.5°）余量：**长期顶在舵机内部止挡上 = 持续堵转 = 发热，是舵机损坏的头号原因**
    （本项目已经烧掉一颗舵机，见接续日志）。
  - ⚠️ **Z 轴方向（哪端算"最高"）尚未拍板** —— 托盘还没装，看着机构判不出来。
    代码里默认 `ZUP` = 2400 µs；装好托盘后若反了，发 **`ZINV 1`** 即可（运行时生效，不用重烧）。
- 舵机**无位置反馈** → 到位靠**时间 + 微动开关**判断，不靠"以为它转到位了"。
- 上电/急停的安全位：⚠️ **目前一律停中位 1500 µs**。
  - 原来写的是"Z 抬到最高 = 2500 µs"，**实测把机构顶死过**：机构可用行程窄于舵机全域时，
    2500 µs 就是限位；而**打开串口会让板子复位**，于是"每开一次串口就顶一次"。
  - **教训：安全位要选"在任何机构上都安全"的位置，而不是"语义上正确"的位置。**
    等托盘装好、方向拍板后，再把安全位改成真正的"Z 最高 / 夹爪张开"。
- **急停语义已改**：`ESTOP` = **冻结舵机（不动）**，不是"回安全位" —— 急停时去动舵机本身就是在制造动作。
  要回安全位请显式发 `SAFE`（`CLEAR` 也会回）。

### 5.3 回零（Homing）

- 顺序：X 先、Y 后（避免两轴同时撞限位造成机械应力）。
- 流程：向原点方向**低速**走 → 碰到微动开关 → 反向退出一点 → 再低速逼近一次（**二次逼近去抖动**）→ 该点记为零点。
- 硬保护：走超过 **理论行程 × 1.2** 还没碰到开关 → `EVT HOME_FAIL code=16`，进 FAULT。
- 回零完成后写入软限位：`[0, 行程]`，并把当前位置置 0。

## 6. 入盒检测（6 路）

规则要求"**货物必须全部进入储物盒才计分**"，所以这一路是**计分依据**，不是装饰。

- 6 路红外对射，接收端接 `PC0~PC5`，内部上拉，**低电平 = 有货挡光**。
- **去抖**：连续 N 次（建议 5 ms × 4 = 20 ms）读到同一状态才认账，再发 `EVT BOX_CHANGED`。
- ⚠️ **采样时机**：必须在**爪子抬起、离开盒口之后**再采 —— 爪子本身会挡光（这条来自 `03_设计与尺寸\框架与布局尺寸.md` §5.1 的定稿口径）。
- ⚠️ **防串光 = 分时扫描**（推荐）：逐个点亮发射管、只读对应那一路。这需要**每路发射管可单独控制**（6 个 GPIO 或 1 片 74HC138 译码），是 §11.3 的待确认项。
- 兜底：即使做了分时扫描，规则里"未全入盒不计数"代价很高，建议保留 **D3 的"俯视相机复核"** 作软件冗余（AI 侧用 `cam_shot` 看一眼柜格）。

## 7. 串口屏代理（✅ 2026-09-22 已实现，fw 0.2.3）

- 屏挂在 **USART3**（`PB10`=TX / `PB11`=RX），与 PC 侧无关。
- 固件提供 `LCD <内容>` **原样透传**，不解释协议 —— 因为淘晶驰的指令集是它自己的方言，让上位机（AI）直接写屏指令最灵活，**改屏的界面一行固件都不用动**。
- 典型用法：AI 发 `LCD page 1` / `LCD t0.txt="第3件：红色方块"`，屏自己显示。
- **`LCD` 会自动补 `FF FF FF`**（淘晶驰每条指令必须以此结尾才会被执行）；要发裸字节用 `LCDRAW <hex>`。
- **波特率**：⚠️ **本屏（TJC4832T135_011R）实测出厂就是 9600**，固件默认值也已是 **9600**（`board.c` 的 `lcd_init(9600u)`）。
  **波特率不对时屏"完全不响应"** —— 它收到的是乱码、不会解析、**一个字节都不回**，而屏幕上毫无异常表现；
  ⚠️ 反直觉的地方：这时**接收端也是 0 字节**（屏不解析就不回答），**不是**收到乱码，所以别把"`count=0`"当成"屏的 TX 没接"。
  - **判据（最省事）**：发一条垃圾指令 `LCD zzz`，若 `LCDRD` 立刻读到 **`1A FF FF FF`**（或 `00 FF FF FF`）⇒ **波特率正确、双向都通**（淘晶驰对无法识别的指令会回错误码）。
  - 换波特率用 `LCDBAUD <n>`（运行时生效，不用重烧），或改 `lcd_init()` 的默认值；也可以在淘晶驰上位机里改屏侧并保存（`bauds`）。
- **帧格式：屏侧是 8N1（不开校验）** —— ⚠️ **别照抄 USART1 的 8E1**，两者帧格式不同是本项目特有的坑。
  （`board.c` 的 `lcd_init` 里 `USART3->CR1` 只设 `UE|TE|RE`，没有 `PCE`/`M`。）
- **`BRR` 要用 PCLK1 而不是 HCLK**：USART3 挂 APB1。当前 8MHz 时 PPRE1=/1 → PCLK1=8MHz；
  **M3 上 PLL 72MHz 后 PPRE1=/2 → PCLK1=36MHz**，那时若照抄 USART1 的算法波特率会**差一倍**。
  代码里已自动从 `RCC->CFGR` 推导（`pclk1_hz()`）。
- **回读**：`LCDRD` 返回屏发来的字节（触摸事件等）的十六进制 —— 排查"屏到底有没有在说话"时很有用。
- **接线**：屏 5V（预留 5V/1A）、GND 与主控**共地**；屏 `RX` ← 单片机 `PB10`(TX)，屏 `TX` → 单片机 `PB11`(RX)（**交叉**）。
- **⚠️⚠️ 中文编码：屏的字库是 `GBK`，PC 侧习惯用 `UTF-8` —— 两者不一致！**（2026-09-23 实测确认）
  - `LCD <内容>` 是**按字节原样转发**的（固件**不做**编码转换）→ **直接发 UTF-8 中文上去，屏上就是乱码**；ASCII 则完全正常（`t0.txt="ABC"` 实测 ✅）。
  - ✅ **ASCII 指令**（`page 0`、`t0.txt="12"`、`pic0.pic=5`）→ `LCD` 直接发。
  - ✅ **中文** → 必须走 **`LCDRAW <hex>`**，字节用 **GBK** 编码。例（实测屏上正常显示"红色方块"）：
    `t1.txt="红色方块"` → `LCDRAW 74312E7478743D22BAECC9ABB7BDBFE922FFFFFF`
  - 🛠 **现成工具：`09_固件\tools\lcd_hex.py`** —— `python lcd_hex.py --file <文本文件>` 直接吐出这串 hex。
    ⚠️ **带双引号的指令必须写进文件再用 `--file`** —— Windows PowerShell 5.1 会把参数里的 `"` 吃掉（实测踩过）。
  - ⚠️ **将来笔记本侧的分拣主程序也必须这么做**（Python 里 `text.encode("gbk")` → 发 `LCDRAW`），否则中文全是乱码；**固件侧不需要任何改动**。
